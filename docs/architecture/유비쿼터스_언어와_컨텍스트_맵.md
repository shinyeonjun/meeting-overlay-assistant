# 유비쿼터스 언어와 컨텍스트 맵 (DDD 전략 설계 초안)

> 상태: **확정 (2026-10-11)**. 코드와 기존 문서(`도메인_분석.md`)를 근거로 정리했고, 6장의 결정을 반영했다.
> 코드 식별자는 당분간 기존 이름을 유지한다. 문서 용어와 코드 이름이 다른 경우는 표에 함께 적는다.

## 1. 원칙

- 같은 말은 같은 뜻으로만 쓴다. 한 개념에는 한 이름만 쓴다.
- 문서와 코드가 같은 이름을 쓴다. 한국어 용어는 문서에서, 영어 식별자는 코드에서 쓴다.
- 이름이 충돌하면 이 문서에서 먼저 정하고, 코드를 그 이름으로 맞춘다.

## 2. 유비쿼터스 언어 (용어집)

### 2.1 회의와 생명주기

| 용어 (한국어) | 코드 이름 | 뜻 | 충돌/주의 |
|---|---|---|---|
| 회의 | `MeetingSession` | 녹음·자막·리포트의 기준 단위. 한 번의 회의 기록 | "세션"이라고 줄여 쓰지 않는다 (아래 충돌 항목 참고) |
| 회의 상태 | `SessionStatus` (draft / running / ended / archived) | 회의의 생명주기 | `draft`는 "생성만 되고 시작 안 함"이다 |
| 복구 필요 | `RecoveryState` | 진행 중 회의가 런타임 없이 끊긴 상태 (`runtime_lost`) | |
| 살아 있는 회의 | `RuntimeLivenessPolicy` | 컨텍스트 또는 하트비트로 런타임이 살아 있는지 판단한 결과 | |

### 2.2 음성과 발화

| 용어 | 코드 이름 | 뜻 |
|---|---|---|
| 실시간 자막 | `live utterance`, `transcript_source="live"` | 회의 중 바로 뜨는 자막. 빠르지만 부정확할 수 있다 |
| 발화 | `Utterance` | 시간 구간과 화자를 가진 전사 한 조각 |
| 정본 | canonical transcript (`transcript_source="post_processed"`) | 회의 후 재전사로 만든 **공식 기록**. 리포트와 노트의 원천 |
| 잠정본 | `transcript_source="post_processing_draft"` | 후처리 중에만 존재하는 임시 기록. 정본이 나오면 교체된다. **"초안(draft)"이라고 부르지 않는다** (회의 상태 draft와 충돌) |
| 후처리 | post-processing | 녹음 재전사 + 화자 분리 → 정본 생성 |
| 정본 버전 | `canonical_transcript_version` | 정본이 새로 만들어질 때마다 올라가는 번호 |

### 2.3 이벤트 (발화에서 파생된 의미)

| 용어 | 코드 이름 | 뜻 |
|---|---|---|
| 이벤트 | `MeetingEvent` | 발화에서 추출된 결정, 질문, 액션 아이템, 리스크, 주제, 맥락 |
| 이벤트 상태 | `EventState` (open, confirmed, answered, resolved …) | 이벤트의 진행 상태 |
| 근거 발화 | `source_utterance_id` | 이벤트가 어느 발화에서 나왔는지 |

### 2.4 리포트

| 용어 | 코드 이름 | 뜻 |
|---|---|---|
| 노트 보정 | note correction | 정본 텍스트를 LLM으로 다듬어 노트 본문의 원천으로 만든다 |
| 리포트 | `Report` (markdown / pdf) | 노트와 이벤트를 묶은 최종 산출물 |
| 리포트 공유 | `ReportShare` | 같은 워크스페이스 사용자에게 리포트를 연다 |

### 2.5 작업 (비동기 job)

| 용어 | 코드 이름 | 뜻 |
|---|---|---|
| 후처리 작업 | `SessionPostProcessingJob` | 정본을 만드는 작업 |
| 노트 보정 작업 | `NoteCorrectionJob` | 노트 텍스트를 다듬는 작업 |
| 리포트 생성 작업 | `ReportGenerationJob` | 리포트를 만드는 작업 |

세 작업은 같은 상태 기계(pending → processing → completed/failed)를 따른다 (`job_lifecycle`). 재시도는 기존 작업을 되살리지 않고 새 작업을 만든다.

### 2.6 참여와 맥락

| 용어 | 코드 이름 | 뜻 |
|---|---|---|
| 참여자 | `SessionParticipant` | 회의에 참석한 사람 (이름 기준, 아직 연락처와 연결 안 됐을 수 있다) |
| 참여자 해석 | participant resolution | 참여자 이름을 연락처로 연결하는 과정. 동명이인이면 사용자가 고른다 |
| 후속 작업 | `ParticipantFollowup` | 참여자 해석이 끝나지 않았을 때 남기는 확인 항목 |
| 회사 | `AccountContext` | 거래처나 조직. **이름은 워크스페이스 안에서 유일하다** (활성 계정 기준) |
| 상대방 | `ContactContext` | 사람. 같은 이름이 여럿일 수 있다 (동명이인) |
| 스레드 | `ContextThread` | 같은 주제로 묶인 회의 흐름 |

### 2.7 신원과 접근

| 용어 | 코드 이름 | 뜻 | 충돌/주의 |
|---|---|---|---|
| 워크스페이스 | `workspace` | 데이터를 나누는 최상위 단위 | |
| 사용자 | `UserAccount` | 로그인하는 사람 | |
| 로그인 세션 | `LoginSession` (예전 `AuthSession`) | 로그인 한 번의 유효 기간 | **회의 세션과 다른 개념** |
| 요청 주체 | `AuthenticatedRequest` (예전 `AuthenticatedSession`) | 요청을 보낸 사용자와 권한 | |
| 접근 규칙 | `can_access_session` | 회의는 만든 사람과 관리자가 본다 | |

### 2.8 지식과 검색

| 용어 | 코드 이름 | 뜻 |
|---|---|---|
| 지식 문서 | `KnowledgeDocument` | 리포트에서 만든 검색 단위 (원본 리포트의 파생 복사본) |
| 지식 청크 | `KnowledgeChunk` | 문서를 자른 조각. 임베딩을 가진다 |
| 검색 | retrieval | 질의로 청크를 찾는다. 요청 사용자가 만든 회의로 범위를 제한한다 |

## 3. 충돌하는 용어 (먼저 정리할 것)

| 충돌 | 현재 상태 | 제안 |
|---|---|---|
| **"세션"** | 회의, 로그인, 실시간 스트림 컨텍스트 세 가지로 쓰인다 | 문서에서 "회의", "로그인 세션", "런타임 컨텍스트"로 나눠 쓴다 |
| **"draft"** | 회의 상태(생성만 됨)와 후처리 중간 기록에 쓰인다 | 후처리 중간 기록은 "잠정본"이라고 부른다 (코드 값 `post_processing_draft`는 나중에 바꾼다) |
| **"live"** | 실시간 자막, 실시간 캡처 컨텍스트, live API 서버 세 가지로 쓰인다 | 문서에서 "실시간 자막", "실시간 캡처"로 구분한다 |
| **"canonical" vs "정본"** | 같은 개념을 영어와 한국어로 섞어 쓴다 | 문서는 "정본", 코드는 `canonical` |
| **"리포트" vs "노트"** | 노트 보정 결과와 최종 리포트를 섞어 쓴다 | "노트"는 보정된 본문, "리포트"는 최종 산출물 |

## 4. 바운디드 컨텍스트

| 컨텍스트 | 핵심 책임 | 주요 집합 (aggregate) | 현재 위치 (코드) |
|---|---|---|---|
| **회의** (Meeting) | 회의 생명주기, 복구 상태 | `MeetingSession` | `domain/session`, `services/sessions` |
| **실시간 캡처** (Live Capture) | 음성 수신, 실시간 자막 생성 | `LiveStreamContext`(런타임, 저장 안 함) | `services/audio` (대부분) |
| **후처리** (Post-Processing) | 재전사, 화자 분리, 정본 생성 | `SessionPostProcessingJob` | `services/post_meeting`, `services/audio/pipeline` 일부 |
| **인사이트** (Insight) | 발화에서 이벤트 추출 | `MeetingEvent` | `services/analysis`, `services/events`, `services/live_questions` |
| **리포트** (Reporting) | 노트 보정, 리포트 생성, 공유 | `Report`, `NoteCorrectionJob`, `ReportGenerationJob`, `ReportShare` | `services/reports` |
| **지식** (Knowledge) | 리포트 색인, 검색 | `KnowledgeDocument`, `KnowledgeChunk` | `services/retrieval`, `services/history` |
| **참여** (Participation) | 참여자 목록, 해석, 후속 작업 | `SessionParticipant`(회의 내부), `ParticipantFollowup` | `domain/participation`, `services/participation` |
| **맥락** (Context) | 회사, 상대방, 스레드 | `AccountContext`, `ContactContext`, `ContextThread` | `domain/context`, `services/context` |
| **신원** (Identity) | 사용자, 로그인, 워크스페이스 역할 | `UserAccount`, `LoginSession`, `Workspace` | `domain/models/user.py`, `login_session.py`, `services/auth` |
| **운영** (Supporting) | 런타임 지표, 준비 상태 | 없음 (비즈니스 규칙 없음) | `services/observability` |

**파일럿 컨텍스트 (잠정): 맥락.** 이유: 집합이 작고, 다른 컨텍스트와 ID로만 연결되며, 규칙이 명확하다(워크스페이스 내 회사 이름 유일). 이 패턴을 나머지 컨텍스트에 적용한다.

## 5. 컨텍스트 간 관계 (컨텍스트 맵)

| 관계 | 상류 → 하류 | 형태 | 넘기는 것 |
|---|---|---|---|
| 회의 → 실시간 캡처 | 회의 | 상류가 허용 여부를 정함 | 회의가 running인지 |
| 실시간 캡처 → 후처리 | 실시간 캡처 | 공개 언어 (발행) | 녹음 아티팩트, 실시간 발화 |
| 후처리 → 인사이트 | 후처리 | 공개 언어 | 정본 발화 (확정된 것만) |
| 후처리 → 리포트 | 후처리 | 공개 언어 | 정본 버전 |
| 리포트 → 지식 | 리포트 | 공개 언어 | 리포트 본문 |
| 맥락 → 회의, 참여 | 맥락 | 공개 식별자 | 회사·상대방 ID |
| 신원 → 모든 컨텍스트 | 신원 | 공유 커널 | 요청 주체, 접근 규칙 |
| 공유 커널 | 여러 컨텍스트 | 공유 | 시간 값, job 상태 기계, 발화/이벤트 공통 enum |

**규칙 (목표)**
1. 컨텍스트는 다른 컨텍스트의 **내부 패키지를 import하지 않는다**. 공개 API(`__init__`에서 내보낸 것)만 쓴다.
2. 집합은 다른 집합을 객체로 들지 않고 **ID로 참조한다**.
3. 저장소는 집합 하나당 하나다. 여러 집합을 한 트랜잭션에서 바꿀 때만 서비스가 조율한다.
4. 자동 검사로 1번을 CI에서 막는다 (파일럿 이후).

2. **완료**: 경계 검사 테스트(`tests/server/platform/test_context_boundaries.py`)로 내부 모듈 직접 import를 막는다.
3. **남은 것 (맥락)**: 저장소 구현(`repositories/context`)과 HTTP 라우트(`routes/context`)는 아직 원래 위치에 있다. 저장소는 infrastructure 어댑터이므로 컨텍스트 밖에 두고 공개 API만 쓰는 현재 구조를 유지한다. 라우트도 같은 원칙이다.
4. **다음 컨텍스트**: 신원 또는 참여 중 하나를 같은 방식으로 옮긴다. 추천은 참여 (맥락과 연결이 많아 경계를 검증하기 좋다).
