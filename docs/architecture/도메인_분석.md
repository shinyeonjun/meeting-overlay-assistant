# 도메인 분석 (DDD 재검토 초안)

> 상태: 초안. 코드를 읽고 정리했다. 도메인 전문가 관점(사용자의 의도)은 아직 확인하지 않았다.
> 목적: 구조를 바꾸기 전에 **무엇이 도메인이고 어디가 경계인지**를 명확히 한다. 이 문서는 코드를 바꾸지 않는다.

## 1. 현재 상태 요약

| 항목 | 수치/관찰 |
|---|---|
| 도메인 모델 파일 | `domain/` 전체 약 40개 |
| 서비스 코드 | `services/audio` 약 9,600줄, `reports` 4,900줄, `analysis` 1,700줄, `sessions` 1,250줄 |
| 저장소 계약 | `repositories/contracts/` 약 12개 (session, utterance, event, job 3종, report, retrieval 등) |
| 테스트 | 501개 통과 (DB 포함 통합 테스트 중심) |

**좋은 점**
- `domain/`은 다른 레이어를 import하지 않는다 (위반 0건).
- 세션/이벤트/job 상태 전이 규칙이 도메인 객체 안에 있다 (`session_state_machine.py`, `event_state_machine.py`, `mark_processing`/`mark_failed` 등).

**문제로 보이는 점**
1. **경계 부재**: 녹음 캡처, 후처리, 리포트, 검색, 연락처/계정, 인증이 `services/` 아래에 평평하게 섞여 있다.
2. **유즈케이스가 인프라를 안다**: `SessionPostProcessingJobService`(596줄)가 DB 트랜잭션, 파일 경로, LLM 분석기, Redis 큐를 함께 다룬다.
3. **상태 전이가 여러 곳에 흩어짐**: 세션 상태는 `MeetingSession` 메서드, `session_state_machine`, `session_service`, `session_coordinator`에 나뉘어 있다. `session_coordinator`와 `session_service`는 start/end/rename을 둘 다 가진다. "진행 중 삭제 금지" 같은 규칙은 `session_service`에만 있다.
4. **중복 정의**: `utc_now_iso()`가 5곳에 있다. `meeting_event.py`는 `domain/events/`와 `domain/models/`에 둘 다 있다(호환 shim).
5. **집합 경계가 흐림**: 세션 하나를 바꾸는 작업이 세션·발화·이벤트·참여자·후처리 job 저장소를 여러 개 건드린다. 트랜잭션 경계가 서비스마다 다르다.
6. **DI 조립이 세 곳**: `dependencies.py`, `wiring/`, `dependency_providers/`가 같은 서비스를 다른 방식으로 조립한다.
7. **지금 발견된 규칙 누락 사례** (1~6번 작업에서 고친 것):
   - 원본 발화가 후처리 중 삭제되던 문제 → "원본은 교체 직전까지 존재한다"는 불변식이 코드에 없었다.
   - lease 만료를 문자열로 비교 → 시각 타입이 도메인 규칙이 아니었다.
   - 하트비트 없는 running 세션을 "고아"로 보던 문제 → "살아 있음"의 정의가 프로세스 메모리에 있었다.

## 2. 제안: 바운디드 컨텍스트

현재 코드에서 드러나는 자연스러운 경계는 다음과 같다. 이름은 임시다.

| 컨텍스트 | 책임 | 현재 위치 | 핵심 개념 |
|---|---|---|---|
| **회의 세션 (Meeting Session)** | 세션 생명주기, 상태 전이, 입력 소스 | `domain/session`, `services/sessions` | Session, SessionStatus, AudioSource |
| **실시간 캡처 (Live Capture)** | 오디오 수신, STT, 부분/확정 발화 생성 | `services/audio` (대부분) | LiveStreamContext, Utterance(live), 레인 |
| **후처리 (Post-Meeting Processing)** | 녹음 재전사, 화자 분리, 정본 교체, 보정 | `services/post_meeting`, `services/reports/jobs` 일부 | PostProcessingJob, 정본 버전(canonical version), 초안(draft) |
| **이벤트 추출 (Insight)** | 발화에서 결정/질문/액션 등 추출 | `services/analysis`, `services/events`, `live_questions` | MeetingEvent, EventState |
| **리포트 (Reporting)** | 노트·리포트 생성, 공유 | `services/reports` (생성/조회) | Report, NoteCorrection, ReportGenerationJob |
| **지식/검색 (Knowledge)** | 리포트 청킹, 임베딩, 검색, 히스토리 | `services/retrieval`, `services/history` | KnowledgeDocument, KnowledgeChunk |
| **참여/맥락 (Participation & Context)** | 참석자, 계정, 연락처, 스레드, 후속 작업 | `domain/participation`, `domain/context`, `services/participation`, `services/context` | SessionParticipant, Account, Contact, ContextThread |
| **인증/작업공간 (Identity)** | 사용자, 세션(로그인), 워크스페이스 권한 | `domain/models/user.py`, `auth_session.py`, `services/auth` | User, WorkspaceMember, AuthSession |
| **운영 관측 (Observability)** | 런타임 메트릭, 준비 상태 | `services/observability` | 비즈니스 규칙 없음 (인프라 성격) |

**컨텍스트 간 관계 (초안)**
- 회의 세션 → 실시간 캡처: 세션이 running일 때만 캡처가 허용된다 (상류가 세션).
- 실시간 캡처 → 후처리: 녹음 아티팩트와 원본 발화를 넘긴다.
- 후처리 → 리포트 → 지식/검색: 정본(canonical) 발화가 확정된 뒤에만 다음 단계로 간다 (발행 언어).
- 이벤트 추출은 캡처(실시간)와 후처리(확정) 두 곳에서 같은 규칙을 쓴다 → 공유 커널 후보.
- 참여/맥락과 인증은 다른 컨텍스트가 참조만 한다 (ID로만 연결).

## 3. 집합(Aggregate) 분석

### 3.1 MeetingSession (루트)
- 불변식 후보:
  - draft → running → ended → archived 순서만 허용 (`session_state_machine`).
  - running 세션만 캡처/후처리 시작 가능.
  - 세션 하나에 정본(canonical) transcript 버전이 하나다.
  - running으로 전이하면 런타임 하트비트가 함께 찍힌다 (2번 작업에서 추가).
- 현재 상태: `MeetingSession`은 상태와 일부 시각만 가진다. 발화, 이벤트, 참여자, 후처리 job은 **별도 저장소**로 관리된다.
- 질문: 발화와 이벤트는 세션의 **내부 엔티티**인가, 별도 집합인가? (현재는 별도 집합 + 세션 ID 참조)

### 3.2 PostProcessingJob
- 불변식 후보: 한 세션에 동시에 활성 job은 하나. attempt_count ≤ max. lease가 만료되면 재claim 가능.
- 현재: job 상태 전이는 도메인에 있지만, **정본 교체**(원본 삭제 → 새 정본 저장 → 세션 상태 갱신)는 서비스가 여러 저장소를 순서대로 호출한다.
- 개선 방향: "정본 교체"를 하나의 도메인 동작(또는 한 트랜잭션 경계)으로 묶는다. 1번 작업에서 트랜잭션으로 묶었지만, 규칙은 아직 서비스 안에 있다.

### 3.3 MeetingEvent (발화에서 파생)
- 불변식 후보: 이벤트는 근거 발화(source utterance)를 가진다. 상태 전이는 `event_state_machine`만 따른다.
- 현재: `domain/events`와 `domain/models`에 이중 정의(shim). 병합(`save_or_merge`) 규칙이 서비스에 있다.

### 3.4 Report / ReportGenerationJob / NoteCorrectionJob
- 세 job 타입이 같은 상태 기계를 복사해서 가진다 (pending/processing/completed/failed + lease).
- 개선 방향: **하나의 Job 개념**으로 일반화하고 타입별 페이로드만 다르게 둔다. 4번 작업에서 큐/worker 중복은 줄였지만, 도메인 모델은 아직 3개다.

### 3.5 Participation / Context
- SessionParticipant, ParticipantFollowup, Account, Contact, ContextThread. 세션과의 관계는 ID 참조다.
- 질문: 참석자 해석(resolution)은 세션 규칙인가, 연락처 규칙인가?

### 3.6 KnowledgeDocument / KnowledgeChunk
- 리포트에서 파생된 읽기 모델에 가깝다. 원본 변경 시 재색인이 필요하다.
- 질문: 지식 문서를 "정본의 복사본"으로 볼 것인가, 독립된 집합으로 볼 것인가?

## 4. 규칙이 새는 곳 (서비스에 있어야 할 규칙이 도메인 밖에 있는 것)

| 규칙 | 현재 위치 | 권장 위치 |
|---|---|---|
| 세션 상태 전이 허용 여부 | `session_state_machine`, `session_service`("진행 중 삭제 금지" 등), `session_coordinator`(start/end/rename을 `session_service`와 같이 중복 보유) | 도메인 (MeetingSession) 한 곳 |
| "살아 있는 세션" 판정 | `session_recovery_service` (하트비트 시각 비교) | 도메인 정책 객체로 분리 |
| 정본 교체 절차 | `SessionPostProcessingJobService` | 도메인 서비스 + 트랜잭션 경계 |
| 발화 시각 정규화 | 리포지토리 로더 (`database.py`) | 인프라 유지 (도메인은 UTC 값 객체만 안다) |
| 재시도 상한 | claim 쿼리 파라미터 + 설정 | job 도메인 규칙 (쿼리는 구현) |

## 5. 상충하는 선택지 (결정 필요)

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 전면 재설계** (컨텍스트별 패키지 + 도메인 우선) | 경계가 명확해진다 | 리스크가 크다. 501개 테스트를 대부분 다시 써야 한다 |
| **B. 스트랭글러 이전** (컨텍스트 하나씩 새 구조로) | 단계마다 테스트로 검증 가능 | 과도기에 두 구조가 공존한다 |
| **C. 현 구조 유지 + 규칙만 이동** (세션 상태 전이, 정본 교체, job 일반화) | 변경 범위가 가장 작다 | 패키지 경계는 그대로 흐리다 |

**추천: B를 기본으로, 그 안에서 C의 규칙 이동을 먼저 한다.**
- 가장 큰 가치는 "패키지 재배치"가 아니라 **세션 상태 전이와 정본 교체 규칙을 한 곳으로 모으는 것**이다.
- 실시간 캡처(`services/audio`, 9,600줄)는 가장 크고 가장 덜 도메인적이므로, 마지막에 건드린다.

## 6. 단계 제안

1. **규칙 목록 확정** (이 문서에 대한 사용자 피드백)
2. **MeetingSession 상태 전이 한 곳으로**: `session_service`와 `session_coordinator`의 중복 검사를 도메인으로 옮긴다. 테스트는 그대로 둔다.
3. **정본 교체를 도메인 동작으로**: 원본 보존/교체/복구 규칙을 명시하고, 서비스는 순서만 조율한다.
4. **Job 일반화**: 3개 Job 모델의 공통 상태 기계를 하나로 합친다.
5. **중복 제거**: `utc_now_iso` 5곳 → 공유 값 객체 하나, `meeting_event` shim 정리.
6. **컨텍스트 패키지 재배치** (마지막): 이미 규칙이 모인 뒤에 폴더를 옮긴다. import 규칙은 자동 검사로 고정한다.
7. **실시간 캡처 정리**: 가장 크므로 별도 계획으로 다룬다.

## 7. 사용자에게 확인하고 싶은 질문

1. **회의 한 건의 "정본"은 무엇인가요?** 녹음 재전사 결과인가, 실시간 확정 발화인가, 사용자가 수정한 최종본인가? 지금 코드는 재전사 결과를 정본으로 본다.
2. **발화와 이벤트는 세션의 일부인가요?** 세션을 지우면 같이 사라지는 게 맞나요? 지금은 cascade 삭제다.
3. **리포트는 여러 번 재생성될 수 있나요?** 재생성되면 이전 리포트는 어떻게 되나요? (현재: 버전 없이 덮어씀 + 공유 기록)
4. **지식 검색의 주 사용자는 누구인가요?** 본인 회의만인지, 워크스페이스 전체인지. 현재 검색은 workspace 단위지만 소유자 필터가 없다(이전 분석에서 확인).
5. **실시간 캡처를 앞으로 어떻게 하고 싶나요?** 로컬 STT만 쓸지, Web Speech(클라우드)도 남길지. 이 답에 따라 캡처 컨텍스트 설계가 크게 달라진다.
